# Security and limitations

- OpenSSL EVP supplies Ed25519 and SHA-256; no custom cryptographic primitive is implemented.
- Local wallet secrets are encrypted with AES-256-GCM. PBKDF2-HMAC-SHA256 derives a 256-bit key from the user passphrase and a random 16-byte salt; each encryption uses a random 12-byte GCM nonce and stores a 16-byte authentication tag.
- The current PBKDF2 count is 310,000 iterations. The database stores the count with each encrypted wallet to support controlled future migrations. Supported values are bounded to 100,000–5,000,000 iterations when loading/decrypting.
- New wallet encryption requires at least 12 passphrase bytes; the application recommends a longer unique passphrase. This is a basic floor, not a claim that every 12-byte string is strong.
- Interactive passphrase input uses POSIX `termios` to disable `ECHO` and `ECHONL`. The reader fails closed when standard input is not a terminal. It restores the prior terminal settings after completion and on SIGINT/SIGTERM interruption; pseudo-terminal tests exercise the no-echo and restoration behavior.
- Passphrases and private keys still exist in process memory while in use. `OPENSSL_cleanse` is used on selected temporary buffers, but there is no guarantee against compiler/runtime copies, swapping, core dumps, process inspection, or memory disclosure.
- SQLite WAL and synchronous FULL are enabled, and block append is committed transactionally. Database files are restricted to owner-only POSIX permissions where supported. Backups, parent-directory permissions, filesystem behavior, and host compromise remain outside this prototype's guarantees.
- SQLite integrity checks and replay-based chain validation detect several classes of structural/logical corruption; they are not a substitute for tested off-site backups or a formal crash-consistency proof.
- v0.7.0 authenticates explicitly allow-listed peers and signs authenticated session frames. v0.8.0 adds deterministic local fork choice and reorganization for the legacy non-Raft peer mode. v0.9.0 adds the durable Raft kernel; v1.0.0 integrates Raft RPCs with authenticated TCP and applies majority-committed canonical Ledger-block commands to each member. This remains a crash-fault prototype, not Byzantine consensus or production finality. v1.2.0 adds snapshot/compaction and atomic snapshot restoration; v1.3.0 adds crash-fault joint-consensus voter reconfiguration over a pre-provisioned roster. v1.4.0 adds application-layer peer-session confidentiality (not TLS); v1.5.0 adds passphrase-encrypted node identity vaults and explicit signed trust-policy replication to provisioned nodes. There is no external audit, hardware-backed key custody, automatic peer discovery, automatic policy broadcast, or real-funds protection.

This software is educational test infrastructure. No production custody or financial security claim is made.

## Shared off-chain settlement boundary (0.2.0)

- Match and Flow share one `SettlementBook` through `FinancialPlatform`. A balance stores `total` and `reserved`; all other operations spend only `available = total - reserved`. Active Match order reservations are checked against the order book and cannot be bypassed through Flow or generic internal transfers.
- Settlement batch updates stage all metadata and map entries before applying balance/journal changes. Match and Flow stage engine state before using that batch API; FinancialPlatform stages a complete candidate and publishes it only after SQLite commits.
- The platform snapshot is protected by an unkeyed SHA-256 checksum and monotonic revision. The checksum detects accidental payload damage; it is not a MAC/signature and does not defend against an attacker who can modify the database and recompute the hash.
- Optimistic revision checks reject stale writers. They do not merge concurrent sessions, make a `FinancialPlatform` object thread-safe, or provide a distributed lock service.
- A wallet address linked to off-chain settlement does not itself deposit Ledger funds. The v0.4.0 Bridge adds a separate, explicit native-FST workflow: deposits are credited only from a confirmed local-chain transaction and are idempotent by transaction ID; withdrawals require an unlocked dedicated vault wallet and aggregate collateral. Synthetic test credits remain off-chain and can make the vault undercollateralized. Ledger block append and platform snapshot commit are separate transactions; the bridge uses persisted signed requests plus retry/reconciliation, not true cross-domain atomicity.
- The persistence design rewrites a bounded complete financial snapshot per successful platform mutation. This is simple and atomic for a local prototype but has O(total snapshot size) write/serialization cost. It is not a high-throughput persistence architecture.


## Native FST bridge boundary (0.4.0)

- Bridge support is limited to native FST on this private chain. A locally included block is not distributed or irreversible finality. The v0.8.0 CLI sync path protects Bridge transaction IDs and pinned confirmation heights during reorganization; this does not supply external chain proofs or distributed finality.
- The vault is a dedicated ordinary encrypted Ledger wallet. It is not a hardware-backed or multisignature custodian. Keep its passphrase and database backup secure; the platform stores no passphrase or private key.
- Withdrawals persist the signed transaction and customer debit before mempool submission. This makes process interruption recoverable, but the platform and Ledger commits are not one atomic transaction. The mempool is durable in SQLite from v0.6.0; retry recognizes a recovered pending transaction and resubmits the exact signed bytes only when the durable admission is absent. Only one pending bridge withdrawal is permitted, and signed pending transfers are not cancellable.
- Collateral checks include all off-chain account FST balances, Flow FST reserves, and pending signed payout/fee encumbrances. Match reservations are included in account totals. Synthetic test credits are not collateral and can trigger a shortfall; withdrawals are refused while undercollateralized.
- A checksum is not authentication. A local attacker able to modify the SQLite database and recompute its hash can alter bridge metadata; use filesystem permissions and backups, and do not treat this prototype as a trustless trust-minimized bridge.


## TCP peer networking and chain selection boundary (v0.5.0–v0.8.0)

- v0.7.0 adds independent Ed25519 node identities and explicit allow-listed peers. The handshake uses fresh nonces, signs the chain parameters and both peer identities, and pins the expected server ID on clients.
- After authentication, every application frame is signed over a digest of the connection-specific handshake transcript, its type, payload and strictly increasing per-direction sequence number. This prevents cross-session replay after reconnecting with the same node identities. Invalid, modified, repeated or out-of-order frames are rejected.
- Node identity private seeds are separate from customer wallets and stored as 32-byte files with mode 0600 and current-user ownership checks. Back them up securely; losing one requires provisioning a new trusted identity. The prototype does not encrypt identity files at the application level; use full-disk encryption and filesystem permissions.
- v1.4.0 protocol v6 adds application-layer peer-session confidentiality: both identities sign a transcript containing fresh ephemeral X25519 public keys; X25519 shared secret material is expanded with HKDF-SHA-256 into separate directional AES-256-GCM keys and nonce prefixes. Each post-handshake frame is encrypted and authenticated with associated data bound to the session, message type, and strictly increasing sequence number. Ed25519 frame signatures remain in place. The ephemeral private keys and derived session keys are cleansed from their owned buffers after use; general process-memory disclosure, swap, core dumps, and compiler/runtime copies remain outside that guarantee.
- This is an application-layer encrypted protocol over TCP, not TLS. TCP/IP metadata (addresses, ports, packet sizes and timing) remains visible, and this protocol is not TLS-interoperable. Use only controlled networks until independent cryptographic review and broader adversarial testing are complete.
- Trust stores are operator-managed allow-lists. v1.5.0 supports explicit signed policy pushes to existing nodes, but there is no certificate authority, automatic peer discovery, automatic cluster-wide policy broadcast, rate limit, reputation system or DoS-resistant admission control. v1.3.0 allowed any trusted identity to request a voter change; v1.4.0 supersedes that behavior with explicit `operator` role authorization.
- The legacy unauthenticated `node-listen` command is loopback-only. Remote binding requires `node-listen-auth` and a non-empty trust store.
- Each node process is a single writer for its own SQLite database. Never open one database from multiple writable processes. The server handles one connection at a time.
- Every candidate block is validated by the local Ledger. Legacy non-Raft peer synchronization retains deterministic local fork choice for the fixed-difficulty protocol: greater height wins and equal-height branches use a lexicographic tip-hash tie-break. That tie-break is grindable and does not provide Sybil resistance or distributed consensus. In v1.0.0, Raft-enabled members instead accept replicated Ledger-block commands only through authenticated Raft RPCs and apply them after majority commitment. The two modes are distinct; direct block import and pull-based chain synchronization are disabled in Raft mode.
- A remote transaction accepted into the durable mempool remains unconfirmed until a locally validated block includes it. Persistence is not consensus or network-wide replication.



## Raft runtime security boundary (1.3.0; historical baseline)

- Each cluster member has an independent Ed25519 node identity. The authenticated transport peer ID is checked against the configured pre-provisioned voter/learner roster and the `from`/`to` fields of every Raft message. Trust is operator-provisioned; there is no certificate authority or automatic identity rotation.
- Raft members are assumed to be non-Byzantine and may crash/restart. The protocol does not tolerate malicious members, forged-but-trusted behavior, or arbitrary state equivocation.
- Raft state, block append, and mempool reconciliation are persisted atomically in one SQLite transaction when applying a committed block. This narrows application-level crash windows but is not a formal guarantee against every filesystem, kernel, storage-controller, or hardware failure mode.
- Protocol v6 (v1.4.0) encrypts authenticated session frames with X25519/HKDF-SHA-256/AES-256-GCM and retains Ed25519 signatures/replay sequence checks. Protocol v7 (v1.5.0) adds signed trust-policy push messages over that encrypted channel. This is application-layer encryption, not TLS; transport metadata remains visible. Neither the cryptographic protocol nor the policy workflow has received an external audit.
- Outbound Raft queues are bounded and use one FIFO worker per remote member. Queue pressure can drop messages; Raft retry/heartbeat behavior is expected to recover. No Internet-scale denial-of-service guarantee is claimed.
- v1.3.0 introduced dynamic voter membership within a pre-provisioned endpoint/trust roster of at most nine total peers. At that release, any trusted identity could submit membership changes; v1.4.0 supersedes this with explicit operator-role authorization. v1.5.0 allows signed policy updates to already-provisioned nodes. v1.6.0 adds endpoint host/port/enabled updates within that fixed roster, but peer-ID discovery and automatic cluster-wide policy broadcast remain unimplemented. Automatic transaction gossip, rate limiting, and production finality are also unimplemented.


## Encrypted peer sessions and operator authorization (1.4.0)

- Authenticated protocol v6 performs mutual Ed25519 challenge-response while binding both fresh X25519 ephemeral public keys into the signed transcript. HKDF-SHA-256 derives distinct client-to-server/server-to-client AES-256-GCM keys and nonce prefixes. Sequence-derived nonces are unique within a session; frame type, sequence, and session binding are authenticated as AEAD associated data. Ciphertext is still signed by the sender identity.
- This is application-layer encryption, not TLS. It does not hide IP addresses, ports, packet lengths, or timing and is not interoperable with TLS stacks. Do not describe it as TLS or claim an external audit. Use controlled private networks only pending independent review.
- Trust-store rows now support `peer`, `operator`, `revoked-peer`, and `revoked-operator` roles/status. Legacy two-column trust files are read as ordinary `peer` identities. Only an active `operator` identity may request Raft voter-set changes; normal peers retain ordinary authenticated peer/Raft-status capabilities.
- `peer-trust-revoke` persists a revocation tombstone. New handshakes are rejected immediately by processes that load that updated trust store; already-established sessions are not forcibly disconnected. Apply the revocation to every node's local trust store.
- `peer-trust-rotate` revokes the old identity and adds the replacement with the old role. This is local trust-store maintenance, not cluster-wide automatic distribution. For node identity rotation, update all peer trust stores, member rosters/endpoints, then perform the joint-consensus reconfiguration before removing the old identity.
- The operator role is locally provisioned, not a distributed PKI or quorum-signed governance system. A compromised operator identity can still request membership changes.

## Encrypted identity vaults and signed policy replication (v1.5.0)

- New node identities can be stored in a 0600 passphrase-encrypted vault. PBKDF2-HMAC-SHA-256 derives an AES-256-GCM key using a random salt; each vault uses a random nonce and a GCM authentication tag. Iteration counts are stored in the file and bounded on load. The vault parser rejects symlinks, non-regular files, files owned by another user, group/world-accessible permissions, invalid sizes, wrong passphrases, and modified ciphertext/tags.
- Existing raw 0600 Ed25519 identity files remain readable to avoid forcing a node-ID change on existing deployments. New vaults encrypt the same kind of Ed25519 seed; they do not make process memory, swap, core dumps, host compromise, or unattended process access safe. There is no hardware-backed key protection or remote unlock agent.
- Protocol v7 carries signed trust-policy requests over the existing encrypted/authenticated peer channel. Policies are canonical full-state snapshots bound to one cluster ID and a positive monotonic policy epoch. The receiving node requires an already authenticated active operator, checks the Ed25519 signature and all peer-ID/public-key bindings, and rejects stale epochs, malformed roles, duplicate identities, wrong clusters, and policies with no active operator.
- Local revocation tombstones are monotonic. A later policy cannot reactivate a locally revoked identity or erase its tombstone by omission. A receiver also refuses a policy that would remove any remote endpoint still in its pre-provisioned Raft roster. Operators must complete membership/endpoint removal before trust revocation.
- Trust-policy installation is atomic at the trust-file level and is persisted before the RPC acknowledgement. A separate integration test restarts the receiving process and verifies the revoked identity is still rejected at handshake time. Policy push is explicit one-node-at-a-time; there is no automatic cluster broadcast or peer discovery. Existing active sessions are not forcibly terminated by a trust-file update; revocation applies to subsequent handshakes.
- The management trust file used by `raft-trust-policy-push` is the complete desired trust policy for the target and must include the target public key for client-side pinning, the active operator signer, all other desired remote cluster peers, and at least one active operator after the update. It is an administrative policy snapshot and may be maintained separately from the target's own local trust file.
- The SQLite schema is unchanged in v1.5.0. The text trust-store metadata line records policy cluster ID and epoch; old two-column trust files continue to load as ordinary peers. Protocol-v6 nodes cannot interoperate with protocol-v7 nodes; upgrade the authenticated cluster and operator clients together.

## Endpoint registry and bounded outbound dispatch (v1.6.0)

- Each Raft node stores a versioned, checksummed endpoint registry at `<database>.endpoints`. The registry is bound to the cluster ID and exact pre-provisioned peer-ID roster. It is created with owner-only permissions and atomically replaced after updates. Startup rejects symlinks, non-regular files, unexpected owner/mode, malformed/checksum-invalid data, a foreign cluster ID, stale/invalid generation, duplicate entries, or roster mismatch.
- Only an authenticated active operator can query per-peer outbound health or update an existing peer's host/port/enabled state. Endpoint changes advance a monotonic registry generation and are durable before the RPC acknowledges. The endpoint registry is local to each target node; operators must update intended nodes individually.
- A peer endpoint cannot be disabled while it is an active Raft voter. Demote it through joint consensus first. The v1.6 endpoint API cannot add/remove peer IDs, discover peers, rewrite voter/learner membership, or replace the pre-provisioned identity/trust roster.
- Outbound dispatch uses a fixed-size shared worker pool (default four, maximum eight), one in-flight message per peer, bounded global/per-peer queues, heartbeat coalescing/drop under pressure, and capped exponential retry backoff. Health reports expose queue and retry counters. This limits outbound work but does not make the serialized inbound event loop concurrent or provide rate-limited Internet-facing admission/DoS protection.
- v1.6.0 keeps protocol v7 and the SQLite schema unchanged. The endpoint registry is a separate file and must be backed up with the node database and identity/trust material.

The above features have not received an independent cryptographic audit. The vault KDF and authenticated encryption use OpenSSL primitives, but the complete protocol, key lifecycle, authorization workflow, and failure model still require external review before any deployment beyond a controlled private lab.
